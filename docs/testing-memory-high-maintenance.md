# memory.high 在线维护与策略迁移

[冻结计划](test-plan-memory-high-maintenance.json)使用已发布preview.4精确ELF6088721c，与原已验证的50671aa协议开发构建进行在线迁移。前置条件是新版自身原生88项、三场景各1800秒开销、两角色各600秒业务和20场景/108项故障完整通过，并核对实际报告摘要链、退出0及独立清理。当前只完成冻结，尚无维护业务通过结论。

## 保留的业务标准

两角色均使用原镜像/start.sh、PG参数、真实容器路径、只读原缓存程序；每容器一份Agent，使用新的私有隔离背板、凭据和loopback DCS。CPU7.2核、内存目标20001980416B、双向64MiB/s及各4096IOPS，原运行时硬上限20GiB。启动/资源就绪300秒、缓存随后45秒且同在300秒内、各实际600秒SQL/API、零错误、最大5秒、p95桶上界1秒、覆盖98%、64MiB完整性和原PID1/PG/缓存不重启标准均保持。宿主开始28GiB/稳态8GiB可用内存、20GiB空闲磁盘标准不变。

## 按用户选择修订内存迁移预期

原[22项合同](test-plan-versioned-candidate-maintenance.json)针对相同硬策略，要求所有控制值/journal字节全程不变。用户已明确改用high，因此新合同先在业务门禁释放前读取运行时原值和两程序只读doctor结果，构造每个阶段的完整八项控制值、journal身份、原值和applied值；之后只按这份预先构造的合同比较，不把实际迁移结果重新当作预期。

旧Agent运行时max=20001980416B、high=max；新版只凭同身份journal恢复自有max至原20GiB，再写high=20001980416B；旧Agent恢复运行时反向恢复high并按旧策略写max。CPU/IO及其他四项始终保持。配置全程保持原字节，旧limits.memory_max仅作兼容输入：新版实际使用high并发出唯一的别名警告，三项必须实际applied，其他警告/跳过都不能算成功。单纯quiesce、程序安装及尚未启用Agent时，内核八项和journal原始字节仍须不变；最终停用须恢复门禁前八项运行时原值和同身份空journal。

## 保留自动回退保护，验证显式反向安装

首次安装后尚未启用新版时，原automatic binary-rollback应成功。新版运行并迁移journal后，第二次自动回退必须拒绝旧快照，且程序、原收据、内核值及当前journal均保持；这不是允许忽略的错误。随后使用已经固定摘要并声明兼容journal v1的原程序，在当前quiesce状态执行显式反向binary-install，建立新的当前状态私有收据，再恢复旧Agent。它不覆盖journal、不跳过原自动回退校验，也不需要新增产品配置参数。

因此每角色有9个命令区间，包含原自动回退尝试和额外显式反向安装；全部必须完整处于原600秒原生窗口内。每角色原11项之外新增“变更快照必须拒绝”和“显式反向安装保持当前high状态”两项，共26项。另有35项纯合同检查覆盖错误身份、丢失原值、pending/conflict、额外资源、不完整设置、意外告警及旧journal配新high等篡改。纯检查不是实际业务验收。

原R71结果和原合同逐字节保留，不能转移旧源时间或将新合同伪装成旧合同未变化。前一程序仍是未发布开发构建，此项不能满足最近两个实际已发布次版本迁移；现有AMD64/5.14/单物理盘环境、默认百分比、真实压力、老化故障和长期门槛仍按[后续安排](plan-memory-high-followup.md)单独推进。稳定1.0及原52项完成声明保持未完成。
