# 相同内核限额下的 Agent 活动对照计划

此计划落实 P01.3/P03.3/P05.2 的下一步定位，不是已执行结果。[写 IOPS 对照](testing-write-iops-comparison.md)出现预定总错误模式，但 A1 是 API/DBS.log 写等待，A2 是 SQL/LWLock 等待，故障类型不同。继续提高 IOPS 或原样重跑不能区分配置约束与 CRG 周期工作的影响。

计划使用同一发布 ELF、同一已冻结 DBS 数据来源、相同手动配置及内核值，以四份事先冻结的独立完整冷副本按 A1/B1/B2/A2 顺序执行。A 为正常活动 Agent；B 为仅暂停本容器精确 Agent 实例的用户态执行，已写入的内核硬限额仍保持。B 的辅助循环仍阻塞等待同一子进程，不通过关闭限制或重试新 Agent 获得更高额度。每个测试容器始终只有一份本地 Agent。

四组均固定原失败后主要稳态额度：CPU 7.2 核、内存 20001980416 字节，实际设备读写 BPS 64700080/37470104、读写 IOPS 83/135。保持原标定基准，不再测速，不调整磁盘、数据库、日志目的地、探针或 CCG。A/B 只改变 Agent 是否执行用户态代码；这是静态配额诊断，不替代原 32 项功能重载/高内存压力矩阵，也不把“暂停 Agent”作为部署建议。

暂停必须通过自己的 pidfd，逐次核对 PID/start_ticks、实际 `/proc/exe` 摘要、所属自有容器叶 cgroup、命令为同一配置的 `crg run`、且 PID 非 1。先固定身份和实际八控制值；B 在原生负载测量前暂停并读回 T 状态，测量期间核对同一实例保持暂停，A 保持正常活动。不得向 PID1、数据库、缓存、观察器或其他容器发信号。所有出口在身份仍匹配时恢复本轮暂停的 Agent，再走原停用/恢复和清理；SIGCONT 不得因 PID 复用作用于其他进程。

生命周期边界应先用已授权隔离节点实测资格：正常 STOP/CONT、目标提前退出、PID/摘要/cgroup 不匹配拒绝、异常收尾恢复、内核值保持、主业务/缓存不被暂停；不得直接跳到四组大负载。冻结实际执行器、计划、完整来源及工具摘要后才启动大负载。

每组保留原生 SQL/API 实际 600 秒、64MiB 校验和、同一数据库启动时间，以及原十项备份/同步/独立恢复内容检查。引擎操作在同一 600 秒业务测量中执行，沿用原截止时间，不修改 30 秒备库 fast stop 或其他 SLA；启动和故障须如实计入。线程、分层设备及唯一轮次 PG 等待工具使用已资格版本，四组完全相同，不能为 B 减少采样开销；无内核栈仍记 unknown。

先独立核对四组来源、全时长/数据/引擎/采集/清理及内核值全程匹配，再判读：仅当两 A 都出现原 SQL/API 超时而两 B 都错误 0 时，记录“本次固定配额下活动 Agent 关联模式”；仍保留共享后端、缓存及时序混杂，不直接宣称产品因果。四组都失败只能说明本次暂停不足以消除错误，不能证明所有 Agent 影响已排除。任何准备或采集不完整均为 inconclusive，不能用剩余组计为有效对照。

如出现可重复的活动关联，再根据逐进程 CPU/IO、状态/日志写入及请求/等待时间定位具体开销并修复；如没有有效关联，保留结果，继续从业务 IO 配额约束与 WAL/日志写回方向定位。任何产品修复仍须回到原额度、两角色及完整 32 项标准复验，不以本诊断通过代替正式验收。

本计划不改变已发布包、全部历史失败、52 项任务定义、原七天句柄/后置、正式 24h 对照或未测硬件条件。
