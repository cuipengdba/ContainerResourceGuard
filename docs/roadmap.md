# 后续十个版本开发规划

> 最新范围：R29只保留CPU/内存/IO独立百分比，各默认20；R30设置前检查cgroup（v1跳过、v2校验）。日志保留，诊断/热重载/升级等深入功能继续。历史扩展资源规划暂缓。详见[当前配置](independent-percentages.md)和[下一版交付](next-version.md)。

规划日期：2026-11-10。基线为已发布的 `v0.1.0-rc.2`。以下十个版本全部是未来计划，不代表功能已实现、测试已通过或生产已部署。RC2 实际结果见 [实测报告](testing-rc2.md)，原规划保存在 [RC2 历史规划](roadmap-rc2.md)。

同日追加：用户已授权规划后持续开发到 1.0。新增 [双资源模式与五个可选参数](resource-modes.md) 设计，以及 [重启身份处理](restart-behavior.md)。在原 40 项基础上新增 P01.5/P01.6/P03.5/P04.5/P05.5/P06.5，共 46 项；每版既有验收继续有效。

同日确认业务验收范围：用户选择先按“原启动链 + /test接口 + SQL + 备份/同步 + 独立恢复”的隔离标准推进，归档为[需求R24](requirements.md)。P01/P02/P05/P10的业务验收均按此范围及已记录指标执行；不等待未知厂商接口规范，不改变24h+24h及至少7天门槛，也不声称生产专用流程已验证。

## 产品约束与排期原则

- 一容器一份 Agent，只控制自身 cgroup；不引入 Operator、CRD、跨容器调度器、宿主机控制守护进程或集群重装。
- 最新R29最小配置为`{}`；仅CPU、内存、标定IO三个独立百分比，各默认20%，旧percent仅部署兼容。R30设置前检测cgroup，v1跳过、v2校验后执行。
- IO 百分比继续指实测标定基准的百分比。R26改为默认自动选盘、辅助进程首次标定/复用；业务独立启动，Agent循环不重复测速，不自动提高用户预算。
- 原业务、原缓存程序和 CRG 独立管理。辅助程序缺失、无权限、崩溃或卡住不能成为业务启动和退出的前置条件；资源控制不接管缓存回收或修改数据库参数。
- 已写入的限额由内核执行。Agent 退出不代表限额消失，安全预检也不能保证业务绝不 OOM；请求值、实际值和未生效原因必须可见。
- 延续自身身份校验、单实例锁、持久化原值和外部改写保护；不写父级 Pod、不管理其他容器、不把跨文件修改描述为原子事务。
- 按发布条件推进，不承诺固定日期。第 1–3 版先解决已知缺口；第 4–10 版按实际业务和硬件证据细化，范围调整须更新本文件及任务清单。
- 下面恰好列出十个计划发布版本；中间必要的补丁版、额外候选版不占这十项。修复可以提前交付，不能为了等排期保留已知缺陷，也不能为了凑版本加入功能。

## 1. v0.1.0-rc.3：业务接入与冷启动修正

**目标：** 解决 RC2 尚未完成的 N10/N15，使合成测试结果能落实到实际 DBS/HISDBS 的隔离克隆业务。

| 任务 ID | 开发内容 | 验收条件 |
|---|---|---|
| P01.1 | 建立 DBS 与 HISDBS 原镜像、原 supervisor、原缓存程序的隔离克隆回归入口；保留原启动链 | 分别记录数据库访问、关键业务 API、缓存程序共存、备份、同步和独立恢复结果；通用 PostgreSQL 冒烟不能替代厂商业务验收 |
| P01.2 | 增加固定额度下的冷启动、解包后启动、备份后启动及原健康探针联合测试；采集 IO 积压和就绪时间 | 在 20%/30% 候选额度中逐项记录预算、数据量、就绪阈值和失败；不自动临时放宽限额或悄悄修改原探针 |
| P01.3 | 根据实测修正 CRG 自身启动、日志持久化与退出路径的额外开销；区分业务额度不足和 Agent 缺陷 | 已知 30s 启动超时有可复现条件、定位证据和处置结论；不以一次成功复测消除原失败记录，不削弱必要的原值日志持久化 |
| P01.4 | 补齐实际 supervisor 版本的接入、完整备份和回退方案；修复业务回归发现的接入问题 | 克隆环境中缺程序、无权限、坏配置、崩溃、卡死、忽略 TERM 均不决定原业务退出；未知脚本拒绝自动修改 |

额度不适合该业务时，应把该额度记录为未通过，并给出容量或原就绪策略的待决项；发布不能宣称任意业务在 20% 或 30% 都能正常运行。生产安装另行执行，不由规划自动触发。

## 2. v0.1.0：首个稳定版

**目标：** 发布在明确环境、业务和额度下可重复部署的稳定基线。稳定版支持范围只包含有证据的组合。

| 任务 ID | 开发内容 | 验收条件 |
|---|---|---|
| P02.1 | 建立 observe 基线与 enforce 持续运行的采集、对比和报告工具 | 每种目标业务至少 24h 基线及 24h 候选额度运行，覆盖一次完整备份/同步高峰；周期更长则延长，不以满 48h 自动判定通过 |
| P02.2 | 把关键业务指标纳入回归：错误、延迟分位数、备份/同步时间、恢复校验、OOM、CPU 节流和 IO 压力 | 测试前记录负载、数据量和可接受阈值，测试后逐项判断；原缓存程序全程参与，失败不可只归因于资源限制后忽略 |
| P02.3 | 在克隆业务中补齐容器重建、Agent 重启、权限撤销、状态目录故障、外部改值、停用恢复及旧版回退 | 身份不串用、不覆盖外部值、原值可追溯；辅助进程故障不改变原业务退出行为，恢复失败必须可见 |
| P02.4 | 发布稳定版安装/卸载/回退手册和精确支持矩阵；冻结首版配置语义 | 明确镜像、内核、运行时、架构、存储及权限条件；区分“已构建”“已测试”“未支持”，不发布未验证组合的稳定性结论 |

前置条件：P01 完成且没有未解决的阻断缺陷。N15 不能靠增加测试超时时间后不作解释来关闭。

## 3. v0.2.0：单百分比安全热重载

**目标：** 将 20% 改成 30% 时不重启业务，也不要求重启 Agent；继续保留严格的配置校验与所有权保护。

| 任务 ID | 开发内容 | 验收条件 |
|---|---|---|
| P03.1 | 增加本地配置重载入口与文件替换检测，兼容原子替换、符号链接切换和短暂缺文件；优先支持 percent 变更 | 合法新配置成为新代次；重复键、错误类型、半写入文件和无法读取时保留上一份有效配置，不清空预算 |
| P03.2 | 实现“校验完整候选配置 → 计算计划 → 逐项持久化/写入/回读”的重载流程 | CPU/内存/IO 分别显示成功、延后或冲突；20→30 只放宽 CRG 自己仍拥有的限额，不突破外部约束，不宣称三项同时原子切换 |
| P03.3 | 显示请求代次、已接受配置、逐项实际值和待完成原因；内存危险下调可在后续周期重试 | 30→20 遇到内存压力时保持原实际值并显示未生效，不能显示整体成功；冲突控制项不反复争写 |
| P03.4 | 规定配置变更的支持范围与模式切换行为，补齐并发重载/重启/disable 测试和文档 | state_dir 变更仍要求受控升级；enforce→observe 不隐式撤销限额，停用恢复继续用明确操作；新增字段不成为必填 |

## 4. v0.3.0：IO 标定质量与多设备

**目标：** 让同一个 percent 在多个数据盘、WAL/备份分盘场景下有清楚、可信的计算依据。

| 任务 ID | 开发内容 | 验收条件 |
|---|---|---|
| P04.1 | 扩展默认自动标定工具：自动选盘、重复采样、离散程度、时间/方法/版本记录与基准有效性检查 | 顺序读写 BPS 和随机读写 IOPS 分开测量并记录；受竞争影响的结果提示质量不足，不伪称设备物理总量，首次辅助进程自动尝试；后续复用，业务不等待 |
| P04.2 | 提供本容器可见设备 profile 的检查、合并、替换和迁移预览工具 | 设备编号变更按稳定身份重识别；替盘、重复身份、旧格式和缺样本有明确处理；新机器不直接套用另一机器性能基准 |
| P04.3 | 完善数据/WAL/备份路径与设备覆盖报告，测试分区、LVM 和选定 device-mapper 栈 | 同层/上下层重复配置可解释地拒绝或跳过；NFS、对象存储、Overlay 等不能确认的路径明确显示未覆盖，不猜设备 |
| P04.4 | 建立至少两个独立块设备和一个选定映射栈的实机回归 | 各设备 BPS/IOPS、共享竞争、profile 缺项/失效分别记录；不把该矩阵外的复杂存储栈宣称已支持 |

此阶段承接 N08/F03 的存储部分。缺少测试设备时标记待验收，不能用单设备结果替代。

## 5. v0.4.0：内存压力与原缓存程序共存

**目标：** 在 RC2 瞬时预检基础上改进持续压力下的解释和下调决策，减少不安全下调及长期不生效却难以定位的情况。

| 任务 ID | 开发内容 | 验收条件 |
|---|---|---|
| P05.1 | 展示可获得的匿名内存、文件缓存、内核内存、events/PSI，以及 swap/HugeTLB 等统计范围 | 缺失的内核字段显示不可用，不拼成虚假的完整总量；只读诊断，不改变 swap、OOM 策略、数据库参数或缓存回收策略 |
| P05.2 | 增加多周期稳定窗口、增长趋势和安全重试策略；复用写前复查与持久化保护 | 并发分配、慢 fsync、持续缓存压力和恢复较低原值时均有测试；危险下调延后，不能为追求“生效”强制回收或擅自加预算 |
| P05.3 | 结合原缓存程序验证高查询负载、备份、WAL 增长和缓存回收重叠场景 | 两个辅助程序互不接管、互不等待，不形成重复回收或重启风暴；记录业务延迟、OOM 和额度未生效时长 |
| P05.4 | 增加长期延后、原预算不适用和统计不足的可操作解释 | 用户能区分“已受控”“等待安全下调”“额度不足”“缺统计”；保持 percent 单参数入口，不保证绝不 OOM |
