# 后续版本规划

日期：2026-11-09。当前已发布版本为 v0.1.0-rc.1，RC2 正按用户“继续开发”的指示实现和回归。本文保留规划与验收标准；实际完成情况见 [任务清单](tasks.md)，不能把未执行场景视为完成。

## 保持不变的产品约束

- 每个容器独立运行一份 Agent，只控制自身；不引入跨容器管理服务。
- 最小配置仍为 `{"percent":20}`，不要求用户分别填写 CPU、内存、IO 限额。
- IO 使用显式标定基准，不在业务启动或运行循环中自动测速。
- 辅助进程启动失败、缺权限、崩溃不能决定原业务退出；不修改原业务逻辑和缓存控制策略。
- 限额在内核中生效，不能承诺 Agent 崩溃时立即自动撤销；资源使用超过预算仍可能影响性能或触发 OOM。

## 版本顺序

| 版本 | 目标 | 发布条件 |
|---|---|---|
| v0.1.0-rc.2 | 补齐故障恢复、严格一对一和接入工具，进入真实业务克隆验证 | RC2 安全任务与可复现回归通过；逐项归档证据 |
| v0.1.0 | 首个经过目标业务验收的稳定版 | 代表性 DBS/HISDBS 业务、缓存控制、备份/同步/恢复和持续运行验证通过 |
| v0.2.0 | 降低日常配置与运维成本 | 稳定版基础上增加本地安全重载和状态展示；不扩大管理范围 |

版本号表示发布成熟度，不把 rc.1 的短窗口合成负载结果等同于稳定版业务验收。架构支持单独列明，arm64 真机结果不足时不宣称已验收。

| ID | 优先级 | 开发内容 | 具体验收 |

| N02 | P0 | 补齐日志持久化与恢复的中断测试，校验每个保存阶段及原值读取 | 写入前/后、回读前/后、恢复中分别强杀；目录满、只读、日志损坏时不丢原值、不误写其他组、不覆盖外部配置 |

| N05 | P1 | 增加清晰的本地诊断输出、安装预检和受控停用恢复流程 | 一条命令可看请求百分比、换算目标、实际上限及跳过原因；停用后辅助循环不重新施加限额，外部值仍保留 |
| N06 | P1 | 提供现有 supervisor 的可审阅接入补丁、原文件备份和回退步骤 | 业务、缓存控制、资源控制独立管理；程序缺失、错误配置、权限不足、忽略 TERM 均不改变业务退出行为 |
| N07 | P1 | 加强 IO 基准校验和覆盖范围展示 | 明确哪些数据路径/设备已覆盖、缺基准和设备变化原因；同设备编号变化可重识别，更换设备不误套旧基准 |
| N08 | P1 | 补充随机读写 IOPS、多设备和设备映射栈测试 | BPS 和 IOPS 独立设置可复现实测；不在同一设备栈盲目重复限流；无额外设备时该部分保持未验收 |
| N09 | P1 | 将候选发布构建、包校验和证据归档接入 CI | 产物与测试二进制可用 SHA256 对应，包内文档链接有效，无凭据、私有 profile 和业务源码 |

## 业务验证与稳定版门槛

建议先在授权测试环境建立同结构克隆，保护原有业务和数据。具体数据量、压测强度与性能阈值在执行前记录，不能根据 rc.1 的简单 shell 测试直接宣布生产可用。

1. 先在 observe 模式采集代表性基线，建议覆盖至少 24 小时及一次备份/同步高峰。
2. 再在候选额度下持续运行，建议至少 24 小时，包含原缓存控制进程。30% 到 20% 只能作为待验证的候选顺序，最终额度应由业务峰值决定。
3. 比较数据库错误、延迟分位数、备份/同步耗时、缓存回收压力、OOM/驱逐、CPU 节流、IO 压力及 Agent 开销。
4. 验证容器重建、辅助进程重启、权限撤销、状态目录故障、外部改写、停用恢复和版本回退。
5. 使用实际备份完成独立恢复并核对数据；出现异常时保留完整记录和回退结果。

48 小时是建议的最低观察窗口，不是“满 48 小时即通过”。没有覆盖完整备份/同步周期或关键性能阈值不达标时继续验证；未完成场景仍保持待验收。

## v0.2.0 候选增强

| ID | 功能候选 | 约束 |
|---|---|---|
| E01 | 修改 percent 后本地安全重载，无需重启业务 | 先完整校验，再分别写入/回读；保留原值和冲突保护，不承诺跨控制文件原子更新 |
| E02 | 在 RC2 人类可读状态基础上增加可选本地指标 | 一个实例只展示自身；只读指标默认关闭，不新增远程控制能力 |
| E03 | 多设备 profile 的更简便维护和迁移检查 | 仍显式标定，不猜测其他节点性能，不把旧基准直接套新设备 |

不优先加入中心平台、跨容器调度、自动放宽用户预算或复杂 Web 管理。当前目标节点均为 cgroup v2，v1 写入支持按实际兼容需求另立任务。

## 归档与状态规则

所有任务在 [任务清单](tasks.md) 跟踪。需求边界见 [需求档案](requirements.md)。每个候选版本分别保存检查点、已知问题、二进制摘要、业务验证范围和未完成项；不能沿用 rc.1 的“通过”替代新功能验收。
