# memory.high 数据保留与 Pod 重建验证

[冻结计划](test-plan-memory-high-cold-rebuild.json)使用已发布preview.4精确程序，前置核对自身在线维护26项、20场景108项故障、真实路径业务、1800秒开销、原生88项及包身份。实际维护报告与退出收据必须和已归档终态完全相同，所有前置测试namespace独立确认消失后才能创建本轮Pod。本轮已完成实际四次启动及独立清理，终态如下。

两角色各做两次启动，共四次、44项，保留[原冷重建合同](test-plan-versioned-candidate-cold-rebuild.json)的300秒PG/API/资源就绪、随后45秒且同在300秒内的原缓存enforce、原ls探针、64MiB/16384行数据、128行marker、备份摘要、独立数据库恢复、原PG参数和真实容器路径。新Pod复用本轮自己的数据库、配置、状态、缓存和日志目录；旧cgroup消失后才创建新Pod。每次须仅有一个精确源程序Agent，以及本次新cgroup内原缓存程序和本次刷新状态，不能凭上次status文件判定就绪。

按用户选择将唯一内存目标映射到规范输入limits.memory_high，目标20001980416B，原运行时memory.max=20GiB保留；CPU7.2核、读写各64MiB/s及4096IOPS不变。每次业务启动门禁前，用原始运行时八项控制值和自身只读doctor预先构造完整控制向量及journal身份、原值和归属；就绪时必须精确匹配，三项全部applied且无其他警告。更换ID后旧journal归档隔离，新journal只对应新cgroup；最终停用恢复新容器原始八项及同身份空journal。

每天0600权限日志须打印v2检测，ID变化后原同日日志保留并追加，手动模式不触发标定。宿主每次初建/重建前至少28GiB可用内存、稳态8GiB和20GiB空闲磁盘要求保持。另一个只读观察程序记录四次Pod UID、父/叶cgroup和原进程身份，待终态核对全部清理。

此项为命名手动预算下的隔离真实路径冷重建，不是默认20%/自动30%持续业务、高内存回收压力、老化故障或七天实测；独立恢复数据库也不等于第二台物理服务器。原旧源44项及长任务时长不转移，缺少的ARM厂商节点、独立物理设备和实际已发布次版本迁移等稳定门槛保持。原52项仍未完成，详见[后续安排](plan-memory-high-followup.md)。

## 实际终态：四次启动、44项通过

[完整报告及原始证据](test-results-memory-high-cold-rebuild.json)确认两角色全部44项通过：四个不同容器ID、四个不同资源身份，保留同一轮数据/状态/日志后的重建均能重新定位自身cgroup。四次完整八项控制值与journal原值/归属均匹配门禁前预声明合同，只有CPU/IO/high三项设置，原20GiB硬上限保持。

64MiB数据、128行marker、备份摘要及独立数据库恢复一致，旧journal完整归档，新journal只属于新身份；同日日志保留并追加，缓存必须是新cgroup内正确程序和本次刷新status。最终停用恢复新容器原始八项及同身份空journal，四次启动无容器OOM。全部四个Pod父/叶cgroup、已记录原进程及runner/worker由独立只读观察确认消失。

此轮没有持续600秒负载、真实high回收压力或长期计时；它不替代这些独立门槛，稳定版和原52项仍未完成。
