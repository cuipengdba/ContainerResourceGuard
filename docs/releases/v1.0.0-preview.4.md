# ContainerResourceGuard v1.0.0-preview.4

本版将内存百分比改为memory.high回收/节流目标，按用户要求不再新增memory.max硬限额。CPU、内存、IO仍各自默认20%，单独配置即可。工程预发布，稳定1.0的完整业务和长期门槛继续。

```json
{"cpu_percent":30,"memory_percent":40,"io_percent":25}
```

- CPU写cpu.max；IO写io.max，百分比按自动标定基准换算；内存写memory.high。手动内存规范字段为limits.memory_high；旧limits.memory_max仍可读取，但解释为high并记录警告。
- high可以低于当前用量，内核尝试回收并节流，允许实际使用超过目标；不能任意释放数据库正在使用的匿名内存。旧内核的同步回收、以及持续高于high的工作集，可能使业务与Agent明显变慢。high自身不调用OOM killer，Kubernetes/祖先硬限额或宿主内存耗尽仍可能OOM。
- 旧CRG写入的memory.max仅凭同容器身份、保留的journal及仍属于自己的applied/pending值恢复原值；随后设置high。外部硬限额、外部更严格high保持；记录缺失、冲突或恢复失败时报告，绝不一律写max。
- 每容器一份Agent；容器/Pod新ID自动发现自身cgroup。设置前检查版本，v1/混合/未知跳过并记录；v2没有权限时降级。默认后台选择最大合格文件系统进行IO标定，无需手填目录。
- 日志一天一个文件，保留30个日历日，超过1,000,000,000字节从最旧日志清理；新增memory_policy及计划警告。辅助程序失败不阻断原PID1启动，已生效的资源节流本身仍会影响业务。

## 下载与升级

[下载页](https://github.com/cuipengdba/ContainerResourceGuard/releases/tag/v1.0.0-preview.4)提供两架构包、SHA256SUMS、构建清单、包检查与验证结果。先在新的私有目录下载实际架构的包并验证摘要：

```bash
curl -fLO https://github.com/cuipengdba/ContainerResourceGuard/releases/download/v1.0.0-preview.4/containerresourceguard-v1.0.0-preview.4-linux-amd64.tar.gz
curl -fLO https://github.com/cuipengdba/ContainerResourceGuard/releases/download/v1.0.0-preview.4/SHA256SUMS
sha256sum -c SHA256SUMS --ignore-missing
tar -xzf containerresourceguard-v1.0.0-preview.4-linux-amd64.tar.gz
./crg build-info
```

每个容器分别升级，保留原配置、IO profile、state_dir和journal，不用空配置覆盖当前配额。私有备份原程序和状态后，用原程序执行quiesce暂停对应CRG写入者并保留内核值与journal；按[安装升级说明](../installation.md)替换程序，再由新程序enable恢复辅助循环。原配置里的三个百分比无需改名，首次新协调会尝试恢复自有旧硬限额并设置high；检查逐项恢复结果及日志，不以进程启动成功代替迁移成功。

不要删除journal或把现存memory.max盲目改成max。若旧状态已丢失或被外部修改，需要按实际部署的原限额另行核对。回退到旧硬策略前，使用当前程序停用并完成恢复，保留匹配的旧配置与程序；回退旧程序会重新采用旧硬限额语义。本次发布不自动更新或重启现有业务环境。
