本版按用户最新选择，将 IO 百分比改为标定读写带宽的百分比；IOPS 只在手动模式显式填写时增加限额。CPU、内存、IO 三项独立配置，未填写各默认 20%，内存继续使用 `memory.high`。这是工程预发布，稳定 1.0 的其余验收继续。

```json
{"cpu_percent":30,"memory_percent":40,"io_percent":25}
```

空配置 `{}` 使用三项各 20%。CPU 写 `cpu.max`，内存写 `memory.high`，IO 只按标定 `read_bps/write_bps` 换算 `io.max` 的 `rbps/wbps`。首次在后台自动选择最大合格本地可写文件系统标定，以后复用匹配的 profile，无需指定标定目录。标定仍记录 IOPS 诊断数据，但不会因此生成默认 IOPS 硬上限。

外部已有 IOPS 限额继续保留。旧 CRG 自有四轴限额仅在原有容器/块设备身份、保留的 journal 及当前值检查成立时，按原基线恢复 IOPS 并设置新带宽；外部改动或状态缺失会报告冲突/降级，不盲目清空限额。计划、状态、构建信息和日志明确记录新策略及实际设备/目标值。

手动模式仍可分别指定 IOPS；省略的轴保留原值。例如：

```json
{
  "resource_mode":"manual",
  "limits":{
    "cpu_cores":4,
    "memory_high":"12GiB",
    "io_read_bps":"50MiB",
    "io_write_bps":"20MiB",
    "io_read_iops":1000,
    "io_write_iops":500
  },
  "data_paths":["/data"]
}
```

每容器一份 Agent，只发现并管理自身 Cgroup，容器/Pod 重建后自动识别新 ID；纯 v2 执行设置，v1/混合/未知版本跳过并记录。没有权限或辅助程序失败时原启动链继续。日志一天一文件，保留 30 个日历日，超过 1,000,000,000 字节从旧文件清理。已生效的节流会影响资源使用和业务速度。

`memory.high` 是回收/节流目标，可以超过设定百分比；它自身不触发 Cgroup OOM killer。CRG 不新增 `memory.max` 硬限额，保留 Kubernetes/祖先原有硬限制，宿主或硬限额耗尽仍可能 OOM。旧自有 `memory.max` 的恢复继续受身份/journal/当前值保护。

## 下载与升级

[下载页](https://github.com/cuipengdba/ContainerResourceGuard/releases/tag/v1.0.0-preview.5)提供两个架构包、SHA256SUMS、构建清单、包检查、完整性检查及验证摘要。在新的私有目录下载匹配架构：

```bash
curl -fLO https://github.com/cuipengdba/ContainerResourceGuard/releases/download/v1.0.0-preview.5/containerresourceguard-v1.0.0-preview.5-linux-amd64.tar.gz
curl -fLO https://github.com/cuipengdba/ContainerResourceGuard/releases/download/v1.0.0-preview.5/SHA256SUMS
sha256sum -c SHA256SUMS --ignore-missing
tar -xzf containerresourceguard-v1.0.0-preview.5-linux-amd64.tar.gz
./crg build-info
```

每个容器分别升级。保留当前配置、IO profile、state_dir 和 journal，私有备份原程序及状态；用原程序 `quiesce` 停止对应 CRG 写入者并保留内核值/journal，再按[安装升级说明](../installation.md)替换程序，由新程序 `enable` 恢复辅助循环。原三个百分比字段无需改名；核对实际 `rbps/wbps`、原 IOPS、`memory.high` 及外部 `memory.max`，查看逐项状态和日志，进程存在不代表迁移成功。

不要删除 journal 或盲目把限额写成 `max`。旧状态已丢失或外部限额被修改时，按实际部署基线处理。回退前由当前程序停用并确认原值恢复，使用匹配的旧程序/配置；旧程序会重新采用其对应 IO 策略。本次发布不自动替换或重启现有业务环境。
