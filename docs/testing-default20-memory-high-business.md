# memory.high 发布程序的默认20%原业务计划

当前[preview.4](releases/v1.0.0-preview.4.md)使用CPU/内存/IO三个独立百分比，各默认20%；内存只写`memory.high`，保留外部`memory.max`。本轮从空配置`{}`和没有profile的新目录开始，不指定标定目录、输出、设备或速率，不复用成功的手动预算。

[冻结计划](test-plan-default20-memory-high-business.json)、[完整冻结原件](test-evidence/default20-memory-high-business-plan.json.gz)和[驱动源码](../tests/default20-high-original-business-frozen-v1/default20-business.py)先行归档。生产程序仍为摘要`6088721cd4846f95b3b71c82f9884e1909797a199d962b50519c9e013de98b4e`，发布源码`180c86ad7986a76526a41575cc1c176d5da98a9c`；八份发布附件和标签不变。

## 两角色与原标准

使用测试节点原DBS/HISDBS镜像准确image ID、原start.sh/缓存supervisor、原PG参数、真实容器目录和只读CCG挂载；动态生成仅本轮使用的隔离数据库凭据，不导出配置或Pod环境。原共享夹具仅只读复制，每角色新的私有背板、回环DCS和测试namespace；确认网络关闭后才释放启动门禁。每个业务容器有且只有一个当前Agent及缓存进程。

原数据库/API/managed总启动300秒，缓存观察45秒且也在总300秒内；空配置始终保持两个字符`{}`。实际CPU按主机核数20%、内存按主机容量20%映射到high，IO按首次自动选取最大合格本地可写块文件系统的标定基准20%计算。检查内核实际回读、三项journal归属、其余控制值和外部硬上限保持、每日0600日志记录v2与high策略。这里IO百分比是标定基准的比例，不是设备物理峰值承诺。

两角色顺序运行原生600秒负载；原SQL/API零错误、最大5秒、p95桶上界1秒、计划样本覆盖至少98%、64MiB/16384行负载、主库不重启、十项备份/同步/独立恢复内容检查与原生命周期标准不改。备份周期只有完整落在成功原生测量内才接受。保留原campaign、native和engine脚本准确字节；没有给这轮加BPF或原生PG诊断，不把其他诊断资格转记为本轮通过。预期每角色7项启动/控制/身份/日志及1项完整业务，共16项；缺少或未执行不能计通过。

## 清理和失败

DBS/HISDBS分别使用固定的新命名空间和独立输出。前一角色协调进程退出、namespace消失、登记进程PID/start实例及叶/父cgroup消失后，才能开始下一角色；业务失败保留，不提高额度、改PG参数、延长原超时或自动重试。原Pod删除120秒、namespace删除150秒界限保持，并保存实际命令退出/输出。最后只按明确清单导出结构化结果、状态/profile/journal与CRG日志，核对长度和SHA256；Pod/环境/数据库凭据及业务数据不导出。

当前为执行前冻结，尚无运行通过结论。节点只读预检时间`2026-11-13T07:13:08.113150+00:00`，前960任务已终态且进程/namespace消失，内存与磁盘满足原28GiB/20GiB克隆前保留量。已有长期测试容器继续运行，所以本轮不是正式独占24小时或开销因果实验。

[旧硬策略默认20%四格失败](testing-three-resource-default20-supplement.md)和[960的SQL失败](testing-full960-native-child-fixed.md)保持原结论。空配置能应用不表示适合这个业务负载；冷启动、解包/备份后启动及30%变化、原52项、长期/老化和支持矩阵继续分别验收，不提前宣称稳定1.0。


[空配置20%实际启动快照](test-start-default20-memory-high-business.json)：节点2026-11-13T07:51:58.042161+00:00确认同一协调器/DBS驱动PID及start仍活跃，DBS在66.292秒就绪且managed，7项启动/默认换算/单Agent/缓存/high-only journal/v2日志检查通过。实际CPU4.8核、high13334654976B，自动选中/etc/crg所在XFS253:0，IO基准20%为读9831622/写4251266B/s、读12/写6IOPS。原生尚在preparing，零计数不代表600秒零错，HISDBS未开始；当前不作业务或稳定接受。见[冻结计划](testing-default20-memory-high-business.md)。


## 同一任务的最终结果

[原始终态与逐角色汇总](test-results-default20-memory-high-business.json)、[22份准确原件、观察/分析源码及下载摘要](test-evidence/default20-memory-high-business.json.gz)已归档。上面的执行前计划和启动快照保留为历史；同一任务最终失败，未重新启动或改预算。原16项记录16、通过14：每角色7项启动与控制通过，完整业务项各失败。15项离线证据核对通过，只说明原件、归属和清理可核对，不是新增业务通过。

HISDBS快照里的零计数不能推导实际零错误；其engine伴随探测记录仍保留。DBS即使记录时长超过600秒，也因中断、错误、覆盖不足及未完成内容验收而不能接受。本轮不接受备份、同步或独立恢复；不使用其它手动预算成功记录代替。

两角色journal准确只含cpu.max、memory.high、io.max；原Kubernetes memory.max=21474836480字节以及其它控制值保持。阶段采样中的high/oom/oom_kill均为0，最高内存不到目标high；这不是内存压力或绝不OOM证明。两个自动选择路径虽为/etc/crg和/data，都是同一最大合格XFS文件系统253:0及同一设备身份。IO比例基于低队深标定，不是物理峰值；本次共享节点里低IOPS与备份超时并存，尚未单独验证因果，不擅自调大profile、额度或原300秒界限。

原campaign的worker exec仍运行清理错误及DBS engine清理超时原样保留；随后Pod删除命令均退出0，独立观察确认两个namespace、自有父叶cgroup及66个登记PID/start实例消失。这一最终清理事实不覆盖前述阶段错误。

三个独立百分比、v1跳过/v2设置、无权限辅助失败继续原启动链，以及每日30天/1GB日志均保持现有产品合同。生产源码、preview.4八项附件和标签未修改。冷启动/解包/备份后启动20%与30%、原52项、正式24h、当前high策略七天28周期、硬件矩阵和正式小版本迁移继续独立验收；稳定1.0尚未发布。
