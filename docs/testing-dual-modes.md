# 双资源模式开发验证（2026-11-10）

本轮是 RC3 开发阶段的隔离资源控制验证，不是 RC3/1.0 发布验收。最终测试程序修订 `fc2e26d9a5e392633434c76065fe6aac320e9891`，版本 `v0.1.0-rc.3-dev`，Linux amd64 二进制 SHA256 为 `dcebdc56f8e1fdd3c58a4a67abe58d3cc4e6b0d4e486a28c7e80fa8671f45eec`。

机器可读结果见 [JSON](test-results-dual-modes-linux-amd64.json)。[该源码 CI](https://github.com/cuipengdba/ContainerResourceGuard/actions/runs/42670115753) 已通过；测试节点 Go 1.22.5 的 race/coverage、vet、6 类可选进程故障和 6 类生成补丁故障也通过。guard 语句覆盖率 58.4%，CLI 10.1%，不能把覆盖率理解为全部业务已覆盖。

## 实际范围与结果

在授权测试节点新建独立命名空间和四个临时 Pod，使用已缓存 DBS 镜像，覆盖原命令为测试占位进程。**没有运行原厂商 start.sh、实际业务 API 或原缓存程序；它们仍是 P01/P02 的待验收事项。**

本轮共有 22 个不同检查项在两个最终二进制阶段中获得通过结果；不是宣称一次完整运行全部通过。原断言失败和较早连接故障保留在下面及 JSON 中。

| 检查 | 结果 |
|---|---|
| 百分比与手动容器一对一 | 不同 cgroup；旧 `{"percent":20}` 继续使用 24 个在线 CPU 的 20%，CPU quota 为 480000/100000 |
| 手动 CPU/内存 | 2.5 核 CPU 时间配额、8GiB 内存写入并回读 |
| 手动 IO 无标定 | 从数据目录发现块设备；10MiB/s 读、5MiB/s 写、50/30 读写 IOPS 写入并回读 |
| 四项 direct IO | 读 10013244.75 B/s，写 5224809.38 B/s，随机读 44.52 IOPS，随机写 28.01 IOPS；各约 6 秒 |
| CPU 实际节流 | 8 个负载线程，约 2.40 核，节流计数增加，目标 2.5 核 |
| 内存硬边界 | 独立 128MiB 上限容器内的 256MiB 分配子进程退出 137，oom_kill 增加 1；占位业务 PID 1 存活 |
| pids_max/cpu_weight | 256 和 200 的设置、回读及恢复通过；尚未把实际任务耗尽或权重竞争比例列为已测 |

IO 结果是单个 XFS/LVM 设备、短窗口 direct IO 测试；允许 25% 短时突发容差。没有将缓存命中、网络文件系统、多个设备合计或复杂设备栈包装成限速已验收。

## 原失败与修正

1. 较早的预备二进制回归在 SSH stdout 出现 Broken pipe 后中止余下步骤；报告已落盘，临时命名空间/数据已清理。之后改成远端独立运行、报告落盘，短连接读取结果。
2. 最终二进制第一次回归在恢复断言处失败：测试错误地假定原 cpu.weight 是 100，实际由 Kubernetes 设置为 1。这不是修改恢复目标的理由。修正测试为捕获 journal 中每项真实 original，与停用后的实际值逐项比较；相同二进制独立复测五项恢复、另容器隔离及业务存活全部通过。原断言失败保留，没有将该次执行改写为全绿。

另有一次源码测试发现开发修改放宽了 memory.max=0 的日志校验，已在提交前恢复原有严格规则并添加/保留回归。恢复时内存采样后再次检查外部值的回归也已通过。
