## 预先绑定的组合

1. 复用已验证手动参考预算与实际原profile；取得初始status、doctor、preflight的JSON和human。
2. 在同一Agent内切换既有通过的独立百分比组合30/30/100，再25/29/80。使用当次可信宿主基数、有效cpuset、全部祖先cpu.max/memory.max及原memory.high独立算出目标；IO仅按准确profile的读写BPS计算，外部IOPS保持。百分比请求与上层裁剪警告、最终目标和内核读回逐项对应。
3. 对每一代取得稳定的配置accepted_hash、generation、state与request_id；空白变化不产生新策略，非法101及坏JSON拒绝并保留上一代有效策略。generation按同一Agent运行周期解释，不作为数据库健康或重启计数。
4. profile覆盖使用原设备几何身份和既有数据路径；额外以独立配置的只读doctor/preflight核对缺失、不匹配及未覆盖路径，确保不重标定、不改活动profile、不删除journal。任何需要影响活动控制的异常路径必须先冻结原值契约，不能临时放宽原门槛。
5. 在测试夹具自身leaf内注入一次明确可恢复的CPU外部变更，验证external_conflict原因、实际值保留、下一次刷新不覆盖及业务连续。外部值不得比已通过参考更紧，不写父组或memory.max。预先绑定原值、Agent期望值、外部值及独立回收步骤；不编辑journal消除冲突。若无法从准确实现证明无损回收，此项只保留未执行并改用独立短生命周期原生夹具，不冒险启动。
6. 最后切回原手动策略，明确disable的恢复/冲突处置结果；取得准确报告，退出及清理全部自有对象。冲突记录未解决不能声称空journal或完整恢复通过。

## 输出及兼容的判定

JSON是结构化字段契约，human是摘要，两者不要求字段数量相同；共同显示的值、原因和语义必须一致。逐字段登记JSON路径、human对应行或明确“仅JSON”，不能把缺少的human行伪称通过。现有humanStatus未打印configuration对象，必须在此表中明确JSON专有的代次字段、记录是否满足原任务，并在需要新增输出时先做实现及版本/ELF重新验收决策，不能只修改验收期待。

快照年龄、writer_lock_held、状态reason_code、数据库SQL/API健康分别报告；未持锁不等于数据库失败，持锁也不等于数据库健康。保留已有JSON键和CLI退出码，禁止为了兼容性测试改写持久快照时间或制造stale布尔字段。只读status前后核对快照字节及mtime，允许独立内存采样和年龄变化。

实现前需固定所有计数、独立目标算法、完整JSON/human字段映射、恢复策略及≤600秒时序预算；静态检查、原生只读准入和唯一启动守卫通过后才运行。实际失败保留原件，不删除或重跑到绿。此设计不证明P08.3未来格式、P08.4镜像持久化、默认20%业务性能或长期老化通过。
