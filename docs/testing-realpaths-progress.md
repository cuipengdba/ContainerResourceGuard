# 真机路径验收：探针修正后复测

2026-11-10，按只读部署核对结果，在测试节点新建原 DBS/HISDBS 镜像隔离克隆，使用 `/root/start.sh`、`/opt/ccg/scripts/business-supervisor.sh`、`/opt/ccg/bin/containercacheguard`、角色配置及 `/opt/postgresql` 等实际容器路径，保留 `/opt/ccg` 只读。宿主源目录是全新私有测试目录，不写业务节点，也不改正在执行的两套 24h 基线。

首轮只填 `{"percent":30}`，没有标定目录/输出参数。自动标定并保存，CPU/内存/IO 均 managed/applied；实际值 7.2 核、20,001,980,416B、读34,285,013B/s、写13,370,186B/s、读48 IOPS、写29 IOPS。测试脚本在 300 秒内未观察到成功探针，停止并清理，未运行后续 SQL/备份/同步/恢复或 HISDBS。第二轮新私有夹具采用手动 7.2 核、相同内存、读写16MiB/s、4096 IOPS，脚本也超时。两次原始失败记录保留。

**后续日志纠正了原先的解释**：两轮 PostgreSQL CSV 日志分别在10:25:35和10:50:33记录 `database system is ready to accept connections`；不能再把脚本超时说成数据库在300秒内未就绪，更不能据此断言 IOPS 预算不足。只读 A/B 复核在原基线的两种镜像上都确认：以 root 直接运行 `pg_isready` 返回127，原因是缺 `libpq.so.5` 搜索路径；通过 `su - postgres -c ...` 使用镜像原登录环境则返回0。错误在私有新增夹具的就绪探针，产品和已有原生负载/引擎验收脚本不使用该错误入口。

第三轮仅修正探针为 postgres 登录环境，并保存每次探针退出码/输出；新建数据，保持原镜像、路径、数据库参数、自动30%四项 IO 上限及原300秒预算。DBS使用RC3候选、HISDBS使用1.0组合候选，顺序执行。DBS已在约53.12秒内同时达到数据库就绪与资源managed，CCG只读挂载及独立缓存enforce检查通过；DBS后续原生/备份短测失败，HISDBS独立复测也未通过，详见下文。原生SQL/API仍要求5秒最大、1秒p95桶上界、零错误。

详见[保留原失败并追加诊断的摘要](test-results-realpaths-percent-first.json)。先前询问的 IO 默认口径不再是解决本次超时的前提，当前代码仍保留读写 BPS/IOPS 四项百分比上限。新的测速结果可能受共享设备负载影响，不承诺不同轮次相同速率。短测不能代替既有24h+24h和至少7天发布门槛。

## 修正探针后的 DBS 自动30%实际结果：未通过业务短测

第三轮数据库就绪及managed在53.124秒达到；CPU/内存为7.2核和20,001,980,416B，IO为读15,614,453B/s、写14,198,679B/s、读24IOPS、写33IOPS。CCG只读和独立缓存enforce通过，自动选盘/标定功能运行成功。

后续周期完成8项数据/备份/流复制/独立恢复内容检查，但临时备库fast stop超过原30秒，清理重试也超时，整轮失败。原生负载被协调器中断于367.805秒，SQL154次有19次错误，最大5.017秒，p95桶上界无法满足；API74次零错，但不足完整600秒。有效载荷完整、主库未重启都不能抵消错误、时长及覆盖不足。详见[本轮失败摘要](test-results-realpaths-percent-dbs.json)。

本轮没有执行HISDBS。为避免遗漏另一套业务，已另行执行HISDBS单角色30%夹具，结果见下文；其结束且独立确认namespace移除后，已开始原先明确的手动预算对照。四项比例上限、300秒就绪、30秒临时实例停止和原生5秒/1秒/零错误条件均不放宽。此轮是真实业务短测失败，与前两轮探针入口错误区别归档，不能相互代替。

周期完成7项内容检查，物理备份211.95秒，协调器因负载未按期限结束而中断仍在运行的逻辑恢复；整轮失败。最后可读原生快照仅覆盖约300.17秒，SQL94次中35次错误，API61次零错误；没有完整最终原生报告，不能据最后快照或进程曾存活宣称600秒通过。见[HISDBS失败摘要](test-results-realpaths-percent-hisdbs.json)。
