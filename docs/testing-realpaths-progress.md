# 真机路径验收：探针修正后复测

2026-11-10，按只读部署核对结果，在测试节点新建原 DBS/HISDBS 镜像隔离克隆，使用 `/root/start.sh`、`/opt/ccg/scripts/business-supervisor.sh`、`/opt/ccg/bin/containercacheguard`、角色配置及 `/opt/postgresql` 等实际容器路径，保留 `/opt/ccg` 只读。宿主源目录是全新私有测试目录，不写业务节点，也不改正在执行的两套 24h 基线。

首轮只填 `{"percent":30}`，没有标定目录/输出参数。自动标定并保存，CPU/内存/IO 均 managed/applied；实际值 7.2 核、20,001,980,416B、读34,285,013B/s、写13,370,186B/s、读48 IOPS、写29 IOPS。测试脚本在 300 秒内未观察到成功探针，停止并清理，未运行后续 SQL/备份/同步/恢复或 HISDBS。第二轮新私有夹具采用手动 7.2 核、相同内存、读写16MiB/s、4096 IOPS，脚本也超时。两次原始失败记录保留。

**后续日志纠正了原先的解释**：两轮 PostgreSQL CSV 日志分别在10:25:35和10:50:33记录 `database system is ready to accept connections`；不能再把脚本超时说成数据库在300秒内未就绪，更不能据此断言 IOPS 预算不足。只读 A/B 复核在原基线的两种镜像上都确认：以 root 直接运行 `pg_isready` 返回127，原因是缺 `libpq.so.5` 搜索路径；通过 `su - postgres -c ...` 使用镜像原登录环境则返回0。错误在私有新增夹具的就绪探针，产品和已有原生负载/引擎验收脚本不使用该错误入口。

第三轮仅修正探针为 postgres 登录环境，并保存每次探针退出码/输出；新建数据，保持原镜像、路径、数据库参数、自动30%四项 IO 上限及原300秒预算。DBS使用RC3候选、HISDBS使用1.0组合候选，顺序执行。DBS已在约53.12秒内同时达到数据库就绪与资源managed，CCG只读挂载及独立缓存enforce检查通过；两种业务的后续600秒原生SQL/API和备份/流复制/独立恢复分别判定，运行中不算通过。原生SQL/API仍要求5秒最大、1秒p95桶上界、零错误。

详见[保留原失败并追加诊断的摘要](test-results-realpaths-percent-first.json)。先前询问的 IO 默认口径不再是解决本次超时的前提，当前代码仍保留读写 BPS/IOPS 四项百分比上限。新的测速结果可能受共享设备负载影响，不承诺不同轮次相同速率。短测不能代替既有24h+24h和至少7天发布门槛。
