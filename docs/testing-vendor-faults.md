# 原镜像可选辅助程序故障与回退

2026-11-10，源码 fc2e26d，二进制与双模式报告一致。DBS/HISDBS 各七种场景，在两轮独立原镜像 Pod 中验证；完整结果见 [JSON](test-results-vendor-faults-linux-amd64.json)。没有修改业务节点，原 start.sh 和数据库参数保留。非回环网络先关闭，原缓存 supervisor/程序与全新状态目录继续使用。

| 场景 | 注入方式 | 两轮业务结果 |
|---|---|---|
| 缺程序 | CRG_BIN 指向不存在的测试路径 | SQL、POST /test、PID 1 存活及 TERM 响应通过 |
| 无权限 | 真实 CRG enforce，cgroup 只读挂载 | 三类写入被拒绝，保持原外部预算；业务通过 |
| 坏配置 | percent=0，真实校验拒绝 | 业务通过 |
| 崩溃 | 测试辅助程序退出 42 | 业务通过 |
| 卡住 | 辅助程序循环等待 | 业务通过 |
| 忽略 TERM | 辅助程序忽略 TERM/INT | 业务退出不被无限阻塞 |
| 回退 | 核对备份 SHA256，使用未接入 CRG 的原 supervisor | 业务及原缓存流程继续运行 |

本轮预设 SQL/API 启动期限 90s、TERM 响应期限 12s，与前一轮资源冷启动的 300s 条件不同，不把它写成原 Kubernetes 探针失败或成功。原 supervisor 在这些 TERM 场景中的退出码均为 0，保持原脚本行为；任意业务退出码的保留仍由已有建模脚本回归提供证据。

第一轮只在 API 就绪时立即检查缓存，14 个快照中部分尚未发现缓存进程/状态。这些 false 记录保留，不推断缓存从未运行。原 supervisor 的 doctor 在备份目录尚未建立时可失败并按 15 秒间隔重试；因此第二轮预先增加最多 45 秒的缓存等待，仍保留原脚本重试逻辑。

第二轮 14 个场景均确认缓存进程和 enforce 状态，随后 SQL 继续通过，PID 1 存活。两轮所有 TERM 均在预设期限内完成，所有本次 Pod 已移除。外层夹具的 mode 字段固定写了 observe，权限场景的实际候选为 enforce；公开 JSON 另加 effective_config_mode 说明，不把该元数据标签当成没有尝试写入。

该结果证明本轮注入下的启动、退出和缓存共存，不保证任意辅助程序故障的所有长期表现。原缓存程序自身卡死、厂商专用 API、长时备份周期及性能验收继续独立跟踪。
