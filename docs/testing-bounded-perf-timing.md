# 有限perf缓冲、实际映射预算与厂商阶段诊断

内存百分比继续使用memory.high，CPU/内存/IO各自默认20%；本轮只改进独立诊断工具，没有修改产品源码、依赖或preview.4附件。[结果](test-results-bounded-perf-timing.json)、[原件](test-evidence/bounded-perf-timing.json.gz)和[自有源码](../tests/bounded-perf-host-frozen-v1/perf_budget.go)、[厂商源码](../tests/bounded-perf-vendor-frozen-v1/vendor-diagnostic.py)均冻结归档。

## 原问题与实现

前轮[厂商阶段诊断](testing-iomap-vendor-stages.md)分别记录230/63项perf丢失和同数BPF输出失败，两角色均在完整性检查失败。新增八个函数增加小块write内事件突发；消费端仍同步核对进程身份及FD元数据。缓冲容量是待验证原因，本轮没有删除身份核对或丢失检查，也没有用新结果回填旧失败。

数据环从每CPU八页改为固定32页；额外元数据页也计入预算。调用perf.NewReader前，按实际perf-event-array的possible CPU slots计算最坏映射，超过16MiB即拒绝该独立工具。数据页为二次幂，不会再被库向上取整。创建后读取本进程自己的maps，只在本地计算perf_event映射数量和总长度，不输出地址或内存内容；实际环数须为正、不超过slots，实际映射须在预算内，Reader.BufferSize须与请求数据大小一致。核对完成后才挂接40个hook。

16MiB只约束perf数据及元数据mmap，不约束Go堆、BPF程序/map或总进程内存；不宣称工具整体内存峰值已被该数字覆盖。CPU离线时库跳过相应环，预算仍按全部slots保守计算；页大小/CPU数超预算或本进程映射无法核对时拒绝采集，不作用于业务PID1。

已核对固定cilium/ebpf v0.17.3的reader/ring源码及摘要：NewReader遍历MaxEntries，离线CPU跳过；数据页取二次幂后加一页元数据。没有升级依赖、改写库或新增tracefs回退。原40-hook/5-map、原五函数、额外八阶段的1至4096字节普通文件线程/cgroup门控、原事件数量和工作期限保持。

## 自有50项资格

原44项名称和范围保留，增加六项：真实32次小块写入及inode/返回值、每次七必经阶段及精确嵌套范围、零丢失完整流、单CPU目标与暂停读取期间完成、实际映射预算、自然清理。原嵌套/递归/缺失配对单元继续执行，并增加预算边界拒绝与映射格式/长度错误拒绝。Linux真机50项全部通过。

新目标仅把自己的亲和性设为单CPU，连续32次143字节普通文件append，共4576字节，跨越新页/已有页。采集器仍暂停读取500毫秒，所有写入在解码开始前结束，全部32次返回143且对应真实inode；七必经阶段逐次可见、线程/cgroup和syscall区间相符。802个原事件和358个完整函数配对均保留，scope错误/剩余项为0；正常/快速端口及原32MiB争用写入也继续验证。

当前节点4096字节页、24个possible CPU slots及24个实际环；每CPU数据131072字节，数据加元数据总映射3244032字节，约3.1MiB，低于16777216字节预算。五个先行用例逐项断言预算，dirty用例原始报告也保存同样实际测量。预算超限、非法页大小、零CPU和极大CPU数的单元均拒绝，不以估计值伪装实测值。

原32MiB并发写、143字节同inode独立FD争用与4096字节DSYNC合计33558671字节，memory.high16MiB和写1MiB/s保持。自有争用write为1362378150纳秒，其中同TID rwsem配对1362322124纳秒；只说明该自有用例，不说明厂商使用同一把锁。14个原实例、270个自有BPF对象及自有叶cgroup独立核对消失，六个目标自然退出0，未强制终止。

## 新厂商副本实际结果

## 后续任务与发布边界

本轮证明有限容量方案在已执行用例中的行为，不能推广为所有突发均零丢失或低开销保证。继续依实际厂商事件检查长write中的阶段与请求原窗口；若仍失败先保留失败并针对证据改进，不能重复相同配置直到碰巧通过。

下一开发任务是把已验证的阶段计时接入原完整600秒压力路径：保留全部11个配置/压力/释放区间、原64MiB原生负载、四秒socket及SQL/API零错误条件，只在新的自有namespace部署独立诊断器，失败也完整保存。需要先验证更长会话的事件/内存预算、原配置切换和压力释放期间的身份与清理，再做一次有新增诊断证据的完整复现；不能把本轮无长写的120秒诊断当作原问题已修复，或重复无新增信息的600秒试验直到碰巧通过。获得可审核的修复后再接受默认20%和完整压力全标准。

原[52项任务](current-task-registry.json)定义和未完成状态、正式24小时、真实high七天604800秒/28周期及老化后置、ARM64/Linux6、多独立设备与实际已发布次版本升级条件继续保留。原长期任务未重启、附加探针或转移旧策略时长。稳定1.0尚未接受，可下载版本仍是[memory.high preview.4](releases/v1.0.0-preview.4.md)。
