# memory.high 策略与600秒独立诊断会话

用户确认：内存百分比只换算为 `memory.high`，不再通过 `memory.max` 设置新限额。CPU、内存、IO分别设置百分比，缺省各20%；Kubernetes/容器运行时已有的硬上限保留。达到high后，内核尝试内存回收并对分配施加节流，允许短时超出；不可回收的业务内存仍需业务自身释放，不能承诺整个系统或父级cgroup绝不OOM。现有[memory.high preview.4](releases/v1.0.0-preview.4.md)已采用该策略，本次只改进独立诊断与文档，没有重新打包产品或修改发布附件。

[结果](test-results-long-perf-session.json)、[完整原件](test-evidence/long-perf-session.json.gz)、[长会话源码](../tests/long-perf-host-frozen-v1/session_limits.go)和[压力调用包装草稿](../tests/full-pressure-hook-draft-v1/crg-full-pressure-hook810.py)已归档。严格每容器一个Agent、权限不足时记录原因并继续原业务、cgroup v1不写控制值、每日文件/30天/1GB日志策略保持。

## 本次实际执行

在97节点使用新的自有进程和文件，原50项检查名称、负载、四秒socket和故障判断保留，新增六项长会话检查，56项全部通过。默认仍只读预检；缺少明确测试标记、PID/start不匹配或会话超过1200秒时，在挂接BPF前拒绝。本轮1201秒负例真实执行，未产生BPF对象。1200秒只是独立工具的会话上界，不是放宽业务期限；本轮采集计划660秒，实际目标运行600秒。

目标每五秒接受一次真实loopback请求，收到请求后执行143字节普通文件append，再返回000，不人为延迟响应。120次请求沿用四秒socket，全部成功；实际持续600.000943430秒，120次write共17160字节。每次write均验证FD/inode、设备号、143字节返回值和七个必经阶段，所有额外阶段都包含于唯一的同线程、同cgroup write区间；folio_wait_stable按是否已有页条件记录，不制造观测值。全部120次请求在原请求时间窗内找到事件发生时保存的精确收发端口。

长会话保存3922个事件、613个syscall配对和1348个函数配对，perf丢失/BPF输出失败均0，无未闭合函数、scope错误或剩余项。原故障满环用例仍报告198515次BPF输出失败并标记incomplete，这是预期故障识别，不能宣传为整套测试从未出现丢失。

## 映射与进程内存测量

固定cilium/ebpf v0.17.3与原八份内核/布局/配对/预算源码保持逐字节一致，没有升级依赖。每CPU32页数据加1页元数据，按实际possible CPU slots在分配前检查16MiB mmap预算，挂接前核对本进程perf_event映射；本次增加读完流后的第二次测量，两次环数、长度和Reader.BufferSize必须一致。

当前节点24个slots、4096字节页、24个实际环，每CPU数据131072字节，实测总映射3244032字节，约3.1MiB。所有实际采集用例的前后映射均一致。新增getrusage MaxRSS，单位为Linux报告的kB，记录到采集结束的观测峰值；其采样在JSON序列化之前，不能表示整个程序及输出阶段的峰值，也不是工具总内存硬上限。16MiB仅约束perf mmap，不包含Go堆、BPF程序/map等。

## 完整压力接入草稿

新增包装层围绕原PressureExecution.business_native调用，保留原调用一次、返回值和原异常对象优先级；启动、保存或结束诊断的普通异常只记诊断失败，仍运行原业务，并尝试清理已创建的诊断器。每次业务调用创建独立控制器，两角色合成用例使用不同实例，重复安装被拒绝。没有把一个Agent改成多容器管理器。

九个合成用例覆盖正常返回、启动无权限、结束失败、原业务失败、业务与辅助同时失败、业务KeyboardInterrupt、保存失败、工厂无权限及两个角色独立实例。它们只验证调用包装逻辑，尚未实现真实collector工厂，也未执行原厂商600秒和11个配置/压力/释放区间，不能作为真机业务验收通过证据。
