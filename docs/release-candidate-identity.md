# 正式版本产物身份准备

本次交付新增[v1.0.0-preview.1工程预发布](releases/v1.0.0-preview.1.md)，使用精确受测候选，稳定1.0条件仍未完成。下文既有“未发布/候选”描述保留原证据时点，以本条发布身份和范围为当前入口。

当前GitHub只有三个0.1.0工程候选/预览发布，尚无稳定1.0，也没有两个已发布的不同次版本可用于关闭P10维护门槛。当前七天实际运行的d370程序内嵌版本为`next-compatibility-contract`，AMD64摘要`3a1ce7dbf5630f8f1c823005ceb4958653c6c235b2ba5026956ca6597f1926f9`；这些事实不随候选构建改变。

为提前固定最终版本的真实产物，已在独立、干净、精确d370源码检出中，用原Go1.27.3配方构建内嵌`v1.0.0`的两个目标。50个生产源文件逐项与当前冻结合同一致，仅使用另一个显式构建版本参数；得到的新摘要独立记录，不覆盖原测试程序、固定d6正式切换候选、既有包或GitHub资产。

[机器记录](test-results-versioned-candidate-identity.json)包含两包/程序/SBOM/清单摘要、14项离线完整性正反例，以及原生AMD64版本身份探测。身份探测没有执行run/资源命令，也不构成业务运行、限额生效或七天验收。另实际比较两个ELF的段摘要，两架构的.text及若干数据段均不同，不能把同源码重新链接说成字节相同。原d370开发程序的时长不能写到新摘要上；源码一致的证据与具体二进制的实际运行证据必须分别列明。

另在不同绝对路径的全新克隆中复建，两程序、两包、两SBOM、清单和校验和八项逐字节一致；这是同一Windows宿主和工具链的复现，不是Linux跨宿主或ARM原生运行证据。

这是尚未发布的候选构建，包内文档也来自d370冻结快照；正式包仍须绑定最终文档修订、重新核对包摘要/来源证明，并核对所需原生、业务、长期与全部52项发布条件。不能通过修改build-manifest/BUILD.json版本字段、改文件名或移动标签将开发程序伪装成已验收正式程序。现有package.py对内嵌清单版本/摘要的检查保持。

正式24h限额阶段也另受原[实时隔离前置](test-results-formal-stage-current-readiness.json)约束：基线实际86400秒完整接受，且没有其他业务测试夹具，才能再核对并启动固定d6阶段。当前七天组件和老化后置需按原顺序清理，不能删除它们来提前通过该门槛，也不把新版本程序替换进旧对照计划。后续新业务验收安排应与这一既有隔离门槛一并排期。
