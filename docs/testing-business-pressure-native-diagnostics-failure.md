# 原生诊断压力联测的提前失败（R203）

本轮[终态报告](test-results-business-pressure-native-diagnostics-failure.json)失败，退出 1；13 项局部检查及 11 个重载/真实压力区间通过，DBS 完整 600 秒、HISDBS 业务及全部 32 项未完成。冻结源码、计划和[开始快照](test-start-business-pressure-native-diagnostics.json)保留。开始记录是历史观察，以终态判断本轮结果。

## 两类实际业务失败

引擎在备库 `pg_ctl -m fast -w -t 30 stop` 返回失败后终止，主原因仍为 `ENGINE_CONTENT`。日志目录按实际文件列表读取，未从 PG 启动时间猜文件名。备库 21:19:27.406 收到 fast shutdown，21:19:58.827 才 shut down，共 31.421 秒。shutdown restartpoint 总 30.038 秒，其中同步 29.693 秒、最长单文件同步 17.883 秒；原 30 秒停库/45 秒命令超时均保持。最终退出不等于在原期限内通过。原 R120 的类似失败保留。

8 项备份/同步/独立恢复内容检查在失败前通过。原 71 个引擎探针中另有 **7 次 API 请求内部 timeout**，内层最大 5.005882 秒，外层最大 5.401711 秒；SQL 探针 0 错误、最大 1.232047 秒。这是部分区间的探针结果，不能替代完整原生 SQL/API 零错误判定。只读线程样本实际有 D 状态，缺少 PG 原生最终诊断，尚未证明 API 超时或同步迟缓的根因。

## 提前退出暴露的诊断缺口

外部引擎先失败时，容器内原生负载仍在运行。当前采集器只接受最终文件，因此以 `NATIVE_DIAGNOSTIC_NOT_FINAL` 拒绝；随后原 namespace 清理移除负载，内存中的逐请求及 PG 采样未落成最终文件。初始 `load.json` 中 SQL/API 的零计数已经过期，不能作为零错误证据。原生日志只留 exit 137，不能仅凭此判定 OOM 或具体退出原因。采集错误未覆盖原 `ENGINE_CONTENT`。

下一步在新版本测试工具中补齐“外部业务已失败后，精确识别并正常终止本轮专属原生 worker，再有界等待最终诊断”的路径：只向匹配 PID/start/cgroup/worker 源码/参数的负载发 TERM，不向 DBS、PG、API 或其他任务发信号；不增加业务运行时限或重试，不把 interrupted/部分报告计作 600 秒通过。错误优先级和未知/超时路径必须实际验证。原 R203 源码不改写。

[185 个原始线程样本](test-evidence/native-pressure203-thread-dbs.json.gz)覆盖已执行的引擎/重载区间；观察器因提前退出被正常终止，报告明确 incomplete。采样 CPU 0.850269 秒，完整观察子进程 CPU 1.078881 秒，峰值 RSS 34604KiB。47 个线程累计 50 个 D 状态样本；CPU throttled 增量 0、采样 memory.events 的 max/oom/oom_kill 均 0，三个 PSI 文件缺失仍为未知。这里只观察 DBS API 进程，不把其等待栈当 PG 后端根因。
