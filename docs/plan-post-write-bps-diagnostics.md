# 写BPS对照后续诊断计划

本计划落实P01.3/P03.3/P05.2，依据[三组实际终态](testing-write-bps-comparison-v2-result.md)。低写BPS在A1失败、A2通过且B仍有API失败，原预定带宽因果模式未成立。此文件是后续任务和约束，不是新工具已经实现或新负载已经执行的证据。

下一步先开发有界、只读的设备状态采集器，与既有请求/PG及线程单调时间轴对齐：只采实际253:0及其已确认父设备的sysfs统计、可用的vmstat/脏页数据和所选自有测试cgroup统计；保留缺失为unknown，设备层级分别统计。采样开销、时钟一致性、重置、设备变更和超限拒绝先在Linux与原厂商镜像资格验证，不触发额外IO测速、全局sync/drop_caches、块设备设置或生产调参。设备统计仍不能单独证明inode写回归属或某次请求因果。

随后如需观察PG内核等待，新增独立版本的白名单与选择器：实际PGDATA为/opt/postgresql/pgdata，不能沿用旧/data路径假设。保留现有已冻结API观察器及原证据；新工具须按本轮测试数据库/应用标记、backend PID/backend_start与/proc start_ticks固定目标、复查身份，拒绝PID复用/目录越界。只读取经白名单过滤的系统调用类别、FD路径和有界栈，不记录SQL正文、寄存器、参数、任意文件内容；不使用ptrace、不发信号、不改业务日志目的地。新采集链先实际资格通过并测量成本，再冻结计划接入完整压力测试。

完整复测保留原两角色、32项、各600秒、64MiB、11重载/压力区间、原配额及错误0/最大5秒/p95≤1秒/覆盖98%条件；不删除失败数据、延长数据库或停库时限、提高原额度来取得通过。所有新增诊断限时/限内存/限文件并故障放行，生产每容器一份Agent不变。只有具备可以区分业务额度不足与Agent缺陷的证据，才决定产品代码修复；未查明时保留失败。

ARM厂商业务和独立物理多盘仍按用户“暂时没有，先推进现有环境”记录未测，不重复索要节点，不改成已经通过。七天原handle继续运行，接受实际604800秒及原后置后，才按原前置进入待执行的正式24h enforce与对照。
