## 预先规定的判读

先要求三组均实际完成600秒且非中断；任何准备、采集或清理不完整均不能作为有效因果对照。只有A1有原SQL/API错误、B错误0、A2再次有错误，才记录“预定IOPS模式出现”；这仍有共享后端、缓存和顺序等混杂因素，不证明通用因果或产品缺陷。其他组合为inconclusive，单独B通过不算解决。执行器自动interpret摘要只报告原生时长与错误模式；准备、采集和清理是否完整由终态的独立复核另行判定，自动摘要不能越过这些条件。三组手动对照不提高原正式百分比验收配额，不关闭任何历史失败。

## 实际启动与保留的拒绝

Windows生成首份计划时，两个Linux路径被表示成反斜杠，节点按完整计划一致性校验拒绝，未创建业务目录。后续只读逐项差异明确仅work_root/source_folder两个字段；保留错误计划和拒绝原件，修正Linux路径表达，未修改源码、额度或标准。一轮私有差异采集SSH超时，独立/proc检查确认该诊断进程已消失且业务目录仍不存在，未因此重启任何业务运行器。

修正后12项默认只读、缺授权标记及计划篡改拒绝检查实际通过，所有业务目标和namespace仍不存在后才启动。开始快照确认三副本已冻结、原运行器/worker和观察器实例存活；A1只有2项启动局部检查、尚未完成重载或600秒。[开始记录](test-start-write-iops-comparison.json)与其压缩原始证据不代表完成或通过。

继续使用原运行器取三组终态、完整请求/线程/设备/PG报告，独立核对namespace/cgroup、原进程消失和各副本配置恢复，再按上述固定判读。全部52任务、原七天句柄与后置、正式24h对照、ARM厂商业务和独立物理多设备条件保持；产品和preview.2程序未改变。

## 三组实际终态与离线复核

原运行器已自然结束；三组原生负载均实际运行600秒、未被终止，完整对照和原件见[终态](test-results-write-iops-comparison.json)与[独立判读](test-analysis-write-iops-comparison.json)。结论：**预定IOPS模式出现，但仍存在混杂因素**。

| 组 | 主策略写IOPS | 实际秒数 | SQL/API错误 | 主检查数 | D观测数 |
|---|---:|---:|---:|---:|---:|
| A1 | 135 | 600.299 | 0 / 4 | 13 | 25 |
| B | 4096 | 600.182 | 0 / 0 | 16 | 0 |
| A2 | 135 | 600.386 | 3 / 0 | 13 | 0 |

A1与A2的SQL/API错误分布不同。预定判据统计两类错误总和，因此模式出现并不表示同一种API故障在A2再次复现；各自请求与PG/线程窗口仍须分别分析。

A1的4个API错误各重叠4个严格请求内DBS.log写D观测，同期所选native SQL客户端为idle/ClientRead，不能代表API的其他数据库后端。A2的3个SQL错误均为query阶段原5秒截止失败，最大SQL耗时5.015秒；所选本轮客户端在三个独立窗口分别出现LWLock/WALInsert、WALInsert与BufferContent、WALWrite。A2的601个DBS线程样本未见D，不能把其SQL失败等同于A1的日志写阻塞。PG等待是独立快照，没有取得阻塞者链或可用的PG内核栈，不据此认定具体磁盘调用的因果。


每组11重载区间和10项引擎内容检查保留；A组业务失败没有因诊断完整而被改成通过。三个完整冷副本虽来自同一冻结基线，仍共享后端及未重置的缓存/写回状态，顺序也固定。即使本次观察到预定模式，也只能成为配置约束与日志写等待关系的线索，不能证明通用IO因果、产品缺陷已修复或提高原正式配额。B组4096只是诊断对照，不是新默认或部署建议。

每组的逐请求、PG、线程和分层设备原件均有摘要；独立核对原运行器/worker、各组原生与观察器实例已消失，三namespace/cgroup不存在，源PG control和关键程序/配置保持，各副本配置/profile恢复。900秒观察器在本轮结束后用自己的pidfd TERM收尾，其报告仍为部分观察，未宣称完整900秒；可选PG内核栈不可用仍为unknown，不以0代替。设备层不得相加，全设备队列不能归给某个请求。
