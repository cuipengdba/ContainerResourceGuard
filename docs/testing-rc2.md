## Agent 稳态开销

在 1 秒检查周期下采样 12 秒，RSS 为 6,912 KiB（6.75 MiB），累计 CPU 时间增加 1 tick，时钟粒度为 100 ticks/s，即约 0.01 CPU 秒、约一个逻辑 CPU 的 0.083%。同期 write_bytes/wchar 增量均为 0，状态和 journal 的修改时间不变。该短样本不构成长期 CPU/RSS 上界；发生限额/错误状态变化时仍需写入。

内存 OOM 场景仅对有 256Mi 运行时外层保护的临时容器执行，CRG 的 0.2% 内存目标为 133,345,280 字节；不对原业务制造 OOM。内存增长、PSI/events、慢日志后的安全跳过由单元测试补充，真实数据库高峰与缓存回收压力仍待 N10。

该测试节点未提供本组 memory.pressure/io.pressure，PSI 分支由单元测试模拟，实机执行用量余量和可用 events 检查；不能把 PSI 模拟说成目标内核上已验证。

## PostgreSQL 引擎场景

从测试镜像取得 PostgreSQL 14.19 程序，在全新目录初始化主库、流复制库和独立恢复库；只使用本地 Unix socket，不调用厂商 start.sh 或外部业务服务。

- 插入 20,000 行并执行 pg_dump。
- pg_restore 到独立新库，对行数和有序摘要核对。
- 主库追加第 20,001 行，检查流复制追平。
- 脚本退出时停止三个测试数据库，保留短窗口证据。

这证明该版本资源预算下这些 PostgreSQL 引擎操作可完成，不等于 DBS/HISDBS API、业务同步机制、原缓存 Agent、真实备份平台或 24h+24h 长时验收通过。

## 归档与局限

公开记录只保存去标识检查点、数值与二进制摘要；不发布内部地址、凭据、设备 UUID、业务配置或数据。包内 BUILD.json 和 SHA256SUMS 用于对应源码、文档打包修订及实际测试二进制。

测试工具最初因 shell 返回值判断和非 root 读取工具目录权限而中断，修正隔离测试工具后重跑，不将中断场景记为产品通过。

最终候选的一次集成流程中，重新解包数据库工具后，30% IO 额度下 PostgreSQL 超过脚本设定的 30s 就绪等待。数据库日志没有配置报错，随后按测试脚本的 fast shutdown 退出；该组累计约 554MB 写入、5,324 次写 IO。准备阶段写入积压是待核实因素，不能只凭这些数据断言唯一原因。保持原预算与 30s 阈值，在新目录单独复测，SQL、备份恢复摘要与流复制全部成功；初始失败仍保留，不代表所有初始化/冷启动满足 30s。

这也是稳定版新增 N15 门槛：初始化/冷启动与原业务健康探针须联合验收。资源程序故障与业务退出解耦，不能保证已施加的 IO 硬限额不会延长数据库就绪或备份时间。

arm64 仅交叉编译；多设备与复杂存储栈仅有部分逻辑测试，尚未实机验收。未改动既有业务 Deployment、业务启动脚本和资源限额。

结束后先在每个临时容器 disable/恢复自有配置，再删除临时 namespace，确认不存在，并删除专用测试数据目录；私有原始报告留存于仓库之外。
