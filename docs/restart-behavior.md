# 容器和 Pod 重启后的 ID 变化

CRG 不把 container ID、Pod UID 或手工拼接的 cgroup 路径作为配置。每次 Agent 新进程启动都会：

1. 读取 `/proc/self/cgroup` 和 `/proc/self/mountinfo`，定位当前命名空间内自身的真实 cgroup。
2. 对比 `/proc/1/cgroup`，要求与容器 PID 1 归属一致，并校验 cgroup v2 与目标路径。
3. 通过内核 boot ID、路径、设备号和目录 inode 生成身份，不能只按相同路径认定是旧实例。
4. 锁定当前 cgroup 目录 inode，避免换 state_dir 后启动第二个写入者。
5. 只有日志身份相同才沿用原值和中断记录；身份变化时归档旧日志，从新目标读取原值、计算并设置限额，不操作旧路径。

运行过程中也会校验身份，变化后停止进一步写入。重新发现或权限检查失败只影响资源控制，不能决定原业务退出。

| 情形 | 处理 |
|---|---|
| 只重启 Agent、cgroup 未变 | 使用相同 state_dir，保留原值和冲突记录 |
| 容器重启、ID/cgroup 变化 | 重新发现并验证身份；保留的旧日志不能恢复到新目标 |
| Pod 重建、UID/路径变化 | 同样重新发现，无需手工修改 ID |
| 节点重启 | boot ID 变化，旧身份记录不能直接套用 |
| 节点迁移 | 百分比取新宿主容量；标定基准必须属于新节点/设备；手动 IO 重新解析数据路径 |
| 程序和配置仅写在旧容器临时层 | 重建后可能丢失，必须通过镜像或持久挂载保留程序、配置和可选启动入口 |

**自动适配 ID 的前提是新容器仍启动 CRG，并能读取自己的配置。** 每个容器 state_dir 独立；程序不调用 Kubernetes API 去补安装，不在旧路径等待固定 ID。

已有重新发现测试见 [RC2 报告](testing-rc2.md)。双模式、状态目录保留/丢失和节点重启组合由 P06.5 继续验收，不把已有短测试等同于全部场景通过。
