# 任务耗尽与 CPU 权重实测

2026-11-10，源码 fc2e26d，二进制与双模式报告一致。使用原 DBS 镜像中的占位 PID 1，两个同 Pod 的独立容器各自启动一份 CRG，各自状态目录与自身 cgroup；没有运行厂商数据库流程。结果及原失败见 [JSON](test-results-pids-weight-linux-amd64.json)。

每容器外部保护 CPU 1、内存 256MiB。CRG 设置 CPU 权重 100 与 400，A 另设置 pids_max=64。两个计算子进程仅把自身绑定到共同允许的一颗逻辑 CPU，未修改父组或节点 cpuset。预先规定 B 的 CPU 用时占比为 72%–88%，并要求足够总 CPU 用时；没有将权重回读代替竞争效果。

| 场景 | 实际结果 |
|---|---|
| 8 秒竞争 | A 2.270s、B 5.763s，B 71.742%；低于 72%，失败保留 |
| 延长为 30 秒，沿用相同占比区间 | A 4.430s、B 25.647s，B 85.270%；本次通过 |
| CPU 节流计数 | 两轮两容器增量均为 0 |
| A 的有界任务耗尽 | 最多尝试 80 次 fork；创建 48 个子进程后返回 EAGAIN，pids.events max 增加 1；子进程 3 秒后退出并回收 |
| 耗尽后的存活 | A/B 的 PID 1 均存活，没有新增 OOM kill |
| 停用恢复 | 两容器逐项等于各自 journal 捕获的真实原值 |
| 清理 | 两轮独立命名空间均确认消失 |

30 秒阶段七项检查全部通过；短阶段三项中权重竞争失败。不同窗口结果存在波动，权重表达争用时的相对优先级，不承诺严格 4:1、指定墙钟响应时间或业务吞吐。原业务高峰、不同调度器与内核组合仍需另测。
