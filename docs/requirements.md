# 开发需求档案

状态以任务清单和测试报告为准。本文件保存用户提出的全部产品约束，不保存服务器密码、令牌、内部地址或业务源码。

| ID | 用户需求 / 约定 | 实现及验收方向 |
|---|---|---|
| R01 | 在 DBS、HISDBS 容器内部限制整个容器的 CPU、内存、IO | 修改自身现有 cgroup，不能只控制某个业务子进程 |
| R02 | 容器、Pod 重建后 ID 会变化，不能手工改路径 | 每次启动根据进程归属和挂载信息发现，不缓存旧路径 |
| R03 | 不使用 Operator，不重装现有 Kubernetes 或数据库 | 独立二进制、可选辅助进程接入现有部署 |
| R04 | 缺权限、无法执行或程序失败时，原容器正常启动运行 | 辅助进程非阻塞；缺失、只读、错误配置、崩溃均不决定业务退出 |
| R05 | 保留原 start.sh、DBS/HISDBS、PostgreSQL 和缓存控制逻辑 | 在现有 supervisor 层接入，不能替换业务启动逻辑或挂钩业务健康探针 |
| R06 | 缓存控制、资源控制、业务由 PID 1 分别管理 | 业务独立启动；两个辅助程序不构成业务启动前置条件 |
| R07 | 自研产品名 ContainerResourceGuard，创建独立 GitHub 仓库 | 独立源码、CI、使用文档、发布物和测试证据 |
| R08 | 一个总百分比，示例 20 / 30，默认同时用于三类资源 | percent 是必填主要参数；CPU=宿主在线逻辑 CPU 数×比例；内存=宿主 MemTotal×比例 |
| R09 | 无需分别填写 CPU 核数、内存字节、IO 速率 | 自动换算，doctor/状态显示计算依据、实际写入值和上层约束 |
| R10 | IO 采用标定基准的硬上限（用户已选定） | 一次显式标定保存设备基准；percent 同时换算读写 BPS/IOPS；启动时不测速 |
| R11 | 严格一容器一程序、一对一，不能一程序管理多个容器 | 生产 CLI 不接受目标 PID/cgroup/容器列表；只发现自身，不扫描其他容器 |
| R12 | 每个容器单独控制资源 | 每容器独立配置、状态和锁；不修改父级 Pod 或其他容器 |
| R13 | 在用户授权的测试服务器执行测试 | 独立临时容器和测试文件；不在现有业务容器中进行破坏性故障演练 |
| R14 | GitHub 清楚说明各种文档和配置 | 中文 README、配置、架构、集成、IO 标定、故障处理、安全边界、测试报告、贡献说明 |
| R15 | 所有开发需求、开发任务归档到 Markdown，不能遗漏 | 本清单、任务清单、变更记录与测试证据保持对应 |
| R16 | 资源设置失败和撤销必须诚实可见 | 逐项状态；已写限制在崩溃后仍生效；恢复仅撤销自己仍持有的配置 |
| R17 | 不因代理与 kubelet/运行时竞争而反复覆盖 | 发现外部改变则暂停对应控制项，报告冲突 |
| R18 | 部署接入需要适配当前服务器实际环境 | 已只读确认业务节点为 Linux 5.14/cgroup v2/K8s 1.26/containerd；写入效果另由测试验收 |

## 语义边界

- 百分比是每容器相对于宿主机的独立上限，不是集群调度预留。多个容器比例之和可能超过 100%，本程序不做跨容器调度。
- IO 是指定标定方法与设备的测量基准百分比，不是可承诺的磁盘物理极限百分比，也不限制网络流量或缓存命中。
- 上层 cgroup、cpuset、运行时限制可能更严格。内部代理不能突破这些边界。
- 故障不阻断业务启动不等于生效的资源限额没有性能影响；内存限制过低仍可能 OOM。
- 当前首版支持 Linux cgroup v2；v1 自动降级观察，不伪称已支持。

## 需求来源

后续改进提议已归档在 [版本路线图](roadmap.md)，对应 N01–N10 任务；这些提议尚未实现，不应混入已确认的 R01–R18 需求完成记录。

按会话先后记录：容器内 CPU/内存/IO 自动控制 → 业务节点只读核对与无权限放行 → 明确 PID 1 和原 start.sh 的关系 → 独立 GitHub 开发与测试节点 → 总百分比简化配置 → IO 标定硬上限选项确认 → 严格 1:1 → 全部需求与任务 Markdown 归档。
