## 语义边界

- 百分比是每容器相对于宿主机的独立上限，不是集群调度预留。多个容器比例之和可能超过 100%，本程序不做跨容器调度。
- IO 是指定标定方法与设备的测量基准百分比，不是可承诺的磁盘物理极限百分比，也不限制网络流量或缓存命中。
- 上层 cgroup、cpuset、运行时限制可能更严格。内部代理不能突破这些边界。
- 故障不阻断业务启动不等于生效的资源限额没有性能影响；内存限制过低仍可能 OOM。
- 当前首版支持 Linux cgroup v2；v1 自动降级观察，不伪称已支持。

## 需求来源

2026-11-10 用户答复业务验收问题：“先按上述隔离验收标准推进”。对应原问题列出的“原启动链 + /test接口 + SQL + 备份/同步 + 独立恢复”；本轮以该范围作为目标DBS/HISDBS验收标准。没有承诺未知厂商专用接口、生产数据规模或正式SLA已验证；这类项目不再作为等待用户补充信息才能继续的前置条件。24h基线/24h限额对照和至少7天综合验收仍按既定时长及预设判定执行。详见[持续验收](continuous-acceptance.md)。

2026-11-10 追加重启处理说明、双资源模式和五个可选参数，并授权持续开发到 1.0。扩展设计见 [双模式](resource-modes.md) 和 [重启处理](restart-behavior.md)，十版总任务扩为 46 项。

RC2 原规划见 [历史路线图](roadmap-rc2.md)，对应 N01–N15 任务。用户在规划后明确要求“继续开发”，已按该规划实现并验证 RC2；不因此把尚未执行的业务验收或设备测试标为完成。2026-11-10 新增“后面十个版本、每版开发内容”的要求，当前 [十版路线图](roadmap.md) 按 P01–P10 编排 40 项未来开发任务。

按会话先后记录：容器内 CPU/内存/IO 自动控制 → 业务节点只读核对与无权限放行 → 明确 PID 1 和原 start.sh 的关系 → 独立 GitHub 开发与测试节点 → 总百分比简化配置 → IO 标定硬上限选项确认 → 严格 1:1 → 全部需求与任务 Markdown 归档 → 下一版规划 → 继续开发 RC2 → 规划后续十个版本及每版开发内容。

2026-11-10 最新追加 R25/R26：先要求“按照DBS和hisdbs的真机路径测试”，随后要求移除默认手工标定步骤，容器内自动选择容量最大的合格磁盘文件系统。此后追加需求覆盖早期“启动绝不测速”的设计限制，改为可选辅助进程首次尝试、业务不等待、循环不重复测速。新增 P01.7 / P10.5，十版任务从46项扩至48项；详细规则、版本归属假定与未测边界见[自动标定设计](automatic-io-calibration.md)。
